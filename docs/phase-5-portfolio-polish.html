Step 5.1 — Architecture diagram

The architecture diagram was built as an SVG file and embedded directly in the README — no external image hosting needed, renders natively on GitHub. Every service is represented with its actual AWS name, color-coded by function, and connected with labeled arrows showing the data flow.

DECISION
Why SVG instead of a screenshot or PNG?

SVG is vector — it scales perfectly at any resolution, renders in dark mode, and lives in the repo as code rather than a binary blob. It's also editable in any text editor. When the architecture changes, the diagram gets updated in the same commit as the code. A PNG screenshot would be stale the moment anything changed.

Step 5.2 — Professional README

The README is the front page of your project. When a recruiter or hiring manager clicks your GitHub link, the README is the first and sometimes only thing they read. It needs to answer five questions immediately:

  • What does this project do?
  • Is it actually live and working?
  • What technologies does it use?
  • What security decisions were made?
  • Where can I read more?

The README answers all five — with a live URL, architecture diagram, tech stack table, security decisions section, cost breakdown, and links to all five blog posts.

Step 5.3 — CloudWatch dashboard

A CloudWatch dashboard was created with 5 widgets covering the full operational picture:

  • Lambda Invocations — tickets submitted per day
  • Lambda Errors — function failures (the one error visible is from the CORS debugging session)
  • Lambda Duration — execution time in milliseconds, showing cold start vs warm performance
  • API Gateway Requests — total HTTP requests across all testing and live submissions
  • API Gateway Latency — end-to-end response time from the user's perspective
DECISION
Why build the dashboard and then delete it?

CloudWatch dashboards cost $3/month each. For a portfolio project at near-zero traffic, that's the largest single line item — more than all the application services combined. The dashboard was built, used for screenshots and documentation, then deleted. The free built-in Lambda and API Gateway metrics are still accessible in the CloudWatch console without a custom dashboard — they just can't be pinned to a single view.

This is exactly the kind of cost-aware decision a cloud engineer makes in a real job. Building something to demonstrate a capability, then removing it when the cost outweighs the value, is good engineering judgment — not cutting corners.

The dashboard showed real data from the build — the invocation spike on April 1st when the system was built and tested, settling to periodic submissions afterward. Lambda duration peaked at 383ms (cold start + DynamoDB write + SES call) and dropped to ~2ms on warm invocations.

Step 5.4 — Security and PII audit

Before enabling GitHub Pages and making the build log fully public, every file in the repository was audited for sensitive data, credentials, and PII. The audit covered 13 categories of sensitive values across all files.

Why some values were left in place

The API Gateway URL in the frontend files is a public endpoint by design — it's what browsers call when submitting tickets. Anyone visiting the site can find it in browser DevTools. Redacting it from the source code while leaving it functional would be security theater. The email address in Lambda is a configuration value, not a credential — it tells SES where to send alerts. Neither poses a real security risk.

What this project demonstrates

This project was built specifically to demonstrate the skills required for a Cloud Engineer or DevOps role at a Canadian company. Here's what each part of the build proves:

  • Serverless architecture — Lambda, API Gateway, DynamoDB, S3, CloudFront all working together
  • Security discipline — least-privilege IAM throughout, OAC on CloudFront, no hardcoded credentials, pre-publication security audit
  • Canadian data residency — deliberate ca-central-1 deployment with PIPEDA rationale documented
  • CI/CD pipeline — GitHub Actions deploying automatically on push, dedicated deployment user
  • Operational maturity — email alerting, billing alarm, CloudWatch observability
  • Cost awareness — PAY_PER_REQUEST DynamoDB, PriceClass_100 CloudFront, dashboard deleted after use
  • Documentation — every decision explained, every tradeoff documented, every mistake included
  • Git discipline — conventional commits, clean history, proper .gitignore, security fixes committed separately
